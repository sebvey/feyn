# Repository glossary

Every term below is **reserved**: it means one thing in the repository's files: code, docs, skills, issues and decisions.
The words in its "Not" column are **banned** for that meaning: never use them where the reserved term applies.
To add a term, open a PR that adds its row here and replaces, in the same PR, the banned words already in use.

**Two glossaries, each at home.** This is the repository glossary: it applies in repository files
(docs, skills, issues, decisions, specs). Each course has its own **course glossary**
(`courses/<id>/glossary.md`), which belongs to the course, follows the course's language and applies
in that course's files. A word may be reserved in both with two meanings (**epic**); a repository
text that speaks of the course's meaning says so ("epic, in the course's sense"). French
course files keep their French section headings (« Objectif », « L'essentiel », « Pièges »…);
the English terms below are how we talk about them in code, docs and issues.

## The things we build

| Term | Means | Not |
|---|---|---|
| **feyn** | the monorepo and the project | "the platform", "the system" |
| **spec** | the contract of a *type of course*: the shape of its courses (structure, drawing contract, checks) and the generic way to teach every course of the type, its **protocol**. Named: `linear-course`. Versioned, one folder per MAJOR in `course-specs/<name>/<MAJOR>/` | "specification" for anything else; never "spec" for an issue or a design |
| **spec directives** | what says how a spec is written and read: the rule model, levels, methods, severity, conformance clause, versions, their normative references, and the tests of a spec's files; one folder per MAJOR under `spec-directives/`, versioned like a spec (`spec-directives/1/README.md`); a spec MAJOR declares the one it follows in its `spec.yaml` | "frame" (the frame of the work is Kanban), "framework", "metamodel" |
| **course** | what one course teaches and how to teach it: its reader-facing files (what it teaches) and its teacher-only files (how to teach it, `teaching.md`), in `courses/<id>/`, identified by its **course id** (`po-essai`) | "content" (banned as a noun for the course), "material", "data" |
| **build** (noun and verb) | producing an output from a course: the **site build**, made by `site-builder/`, the **classroom build**, made in two halves, the spec MAJOR's `teacher/build/` rendering the parts of the **composition** as text and `classroom-builder/` realising them in Claude Code. Builds have no version of their own | "render" for a build (rendering the parts as text, `render-parts`, is a step of the classroom build), "generate", "export", "compile", "publish" (a release, below) |
| **site** | the published website and its engine (`site-builder/`) | "website", "web", "pages" |
| **teacher** | the generic Claude Code agent that teaches: a `CLAUDE.md` and the teacher skills of its moments, built from the teacher template (`classroom-builder/`), the protocol and the lexicons of its spec, as the **composition** of its spec says | "prof", "tutor", "coach", "agent" alone |
| **classroom** | the folder built outside the repo by `classroom-builder/`, from the parts the spec MAJOR's `teacher/build/` renders, where the teacher runs: `CLAUDE.md`, the teacher skills of the moments and the permissions (`.claude/`), course copy, `course.lock`, `learner/`, its own git; what it gives the teacher, part by part, is the **composition** | "workspace", "instance", "environment" |
| **learner** | the person being taught; **learner memory** = `learner/` | "student", "user" |
| **maintainer** | Seb: owns decisions, releases, freezes | "owner", "admin" |
| **contributor** | anyone who delivers an issue by PR (course files or code) | "author", "developer" |

## Inside a course

| Term | Means | Not |
|---|---|---|
| **domain** (course) | an ordered group of concepts with its own page and presentation. Course vocabulary only: never a part of the repo (that is an **area**) | |
| **concept** | a numbered unit of the course (`0`..`17`, `A1`, `A2`); its **concept folder** holds `concept.md`, `teaching.md`, `sources.md`, diagrams | "fiche", "lesson", "chapter", "page" |
| **numbered concept** | a concept whose number is an integer (`0`, `1`…): it belongs to exactly one domain, and the numbered concepts come first in course order | "regular concept", "main concept" |
| **annex** | a concept numbered `A1`, `A2`…, listed in `annexes` of `course.yaml` (« annexe »): it belongs to no domain and comes after the numbered concepts | "appendix", "bonus concept" |
| **sub-concept** | a node of a concept's teaching tree (`9a`, `9a1`); a **leaf sub-concept** is, as a rule, one teacher message with one question | "section", "step", "unit" |
| **objective** | what the learner can do after the concept (one sentence; `course.yaml` field, « Objectif » section). One term for the current « Objectif » and « À la fin, l'apprenant sait » | "goal", "outcome", "aim" |
| **reader text** | the reader-facing explanation of a sub-concept in `concept.md`, what the site shows | "body", "content", "copy" |
| **reader-facing** / **teacher-only** | the two visibility classes of course files: `concept.md`, `sources.md`, diagrams are reader-facing; `teaching.md` is teacher-only | "public" / "private" (those describe the repository) |
| **teaching notes** | the whole of `teaching.md`, the example bank included: the instructions (« Consignes »), the storyline facts used, the example bank, the drawing instruction (« Schéma ») | "guide", "notes", "answers" |
| **example bank** | the set of **cases** of a concept, in its teaching notes | "examples", "exercises", "questions" |
| **case** | one entry of the bank: situation, question, expected answer, common mistakes, follow-ups; its **title** is its id (learner memory cites it). The bank's heading, « Banque d'exemples », keeps its French word: the entries under it are cases, never called examples | "example", "exercise", "scenario" |
| **practice case** | a case qualified « entraînement » (`qualifiers.practice`): more practice on what a validated concept taught, posed when the learner asks to practise, or unasked at the resume to retrieve a concept validated in an earlier session (rule `earlier-concept-retrieved-at-resume`), without re-explaining. The other qualifiers make a **fallback** case (« rechange ») and an **aside** case (« aparté ») | "dig case", "exercise" |
| **example** | in a teacher message, the illustration that precedes the question (« Exemple »); a case may serve as one, but the heading « Banque d'exemples » names the bank of cases, not a list of examples | the bank's cases |
| **follow-up** | the targeted re-question after a partial or wrong answer (« relance »); ranked 1 or 2 | "retry", "hint", "probe" |
| **storyline** | the running world the cases live in (the bike-share operator); `storyline.md` | "red thread", "thread", "fil rouge", "narrative" |
| **stances** | the standing of each claim of a concept, structured in the frontmatter: **consensus** (Scrum Guide, established practice), **school** (short for school of thought: a named author's or current's choice, « choix d'école »), **course** (this course's own choice, « choix du cours »). A stance is also any stated position of a course (« une équipe en sprints ») | "schools", "opinions", "positions", "status" |
| **neighbors** | the neighbouring notions not to confuse with the concept (« notions voisines »); a frontmatter key of their own, not a stance | "related", "see also" |
| **sources** | `sources.md`, which traces the body of `concept.md`: **claims** (« Affirmations »: claim, section, source, verified, **nature**: consensus, school, course, or **fact**, « fait », what a source states with no stance), **references**, **unverified**. A stance or a neighbour is sourced in its frontmatter item: `refs` and `verified`, the quotation and its place per reference | "bibliography", "citations" |
| **diagram** | an SVG of a concept under the **drawing contract**, with its **caption** | "schema" (data), "figure", "image", "illustration", "schéma" |
| **drawing contract** | the SVG rules of the spec, `course/README.md` 6.1 (viewBox, currentColor, three classes, `<text>`, named groups); the style of 6.2 is not part of it | "style guide" |
| **pitfalls**, **essentials**, **quick test** | the « Pièges », « L'essentiel », « Le test rapide » sections | |
| **deepening** | the optional « Approfondissement » section of `concept.md` (`headings.deepening`): more matter on the concept, sourced in `sources.md`, built by the site, read by the teacher in an aside on the learner's request; no case relies on it. Not a **practice case**, which is more practice on what the concept taught | "dig", "reserve" |
| **concept reference** | in reader text, the words that name a concept, a sub-concept or an annex: « concept 4 », « concepts 5 et 7b », « annexe A2 » (« renvoi »; the lexicon group `concept_refs`, `course/README.md` 3.5). Not the **references** of `sources.md` | "reference" alone |
| **course glossary** | `courses/<id>/glossary.md`, course material | this file |
| **defining concept** | the concept of a course glossary row (its fourth column): the concept a learner opens to dig into the term, the one whose reader text teaches it (`course/README.md` section 5). Not a concept that only uses the term or defines it in passing | "introducing concept", "first concept" |

## How the teacher works

| Term | Means | Not |
|---|---|---|
| **protocol** | the pedagogical protocol: the testable teaching rules of a spec, each named by a slug, set in families and **groups** of rules, each group named by a slug too (`onboarding`) | "the loop", "pedagogy", "rules", "behaviour" |
| **lexicon** | a file of the words of a spec, written once and read by key: `course/lexicon.yaml`, the words a program recognises in a course file (headings, case fields, qualifiers, markers, natures, concept references, source types, typography, the word lists of the checks), read by the checks, the classroom build and the site; `teacher/lexicon.yaml`, the words the teacher says and writes. Not a translation file: the language is the spec's, `language` in `spec.yaml` (decision `lexicon-not-language-pack`) | "language pack", "i18n", "locale", "strings" |
| **teaching session** | always qualified (the other sense is a **work session**): one conversation between the teacher and a learner; **resume** = the first message of a teaching session with an existing learner; **onboarding** = a new learner | "session" alone, "course session" |
| **course path** | « le fil »: the course as the teacher leads the learner through it, concept after concept in course order; the teacher proposes to come back to it after an aside (`course-path-offered-after-aside`). Not the **storyline** (« fil rouge »), nor a domain's « Le fil des concepts » (`concept_thread`) | "main line", "track" |
| **concept status** | where a learner stands on a concept, in learner memory (`learner/parcours.md`, lexicon group `status`): validated, in progress, skipped, to review; a concept absent from the table is to do. Not the Project's **Status** (an issue's), nor the `status` key of a decision's frontmatter | "state", "level" |
| **save point** | a moment where the teacher writes and commits learner memory | "checkpoint", "sync" |
| **composition** | what a teacher is made of, beside how it behaves (the protocol): five parts (`permanent`, `on-demand`, `course-reads`, `learner-memory`, `permissions`), each defined by when it loads and what it draws from the spec, the course, learner memory and the classroom; data in `course-specs/<name>/<MAJOR>/teacher/composition.yaml`, described by `teacher/README.md`, "Composition", with no Claude Code term: its realisation is `classroom-builder/`'s | "architecture", "the instructions" |
| **mini-recap** | the five-line recap every 3 or 4 validated concepts | "summary" |
| **course.lock** | the classroom's record: course id, ref, course sha, tooling sha, channel, `site_url`, date | "manifest" |

## Rules and checks

The **spec directives** (`spec-directives/1/README.md`) and, for the categories and the checks of a
spec, the `README.md` of its MAJOR (decision `rules-with-level-and-method`).

| Term | Means | Not |
|---|---|---|
| **rule** | the unit of a spec, which binds a product (a course or a teacher): one provision held as data in a rule file (`course/rules.yaml`, `teacher/rules.yaml` of `course-specs/<name>/<MAJOR>/`), apart from the prose that describes it, with an `id` (a slug), a **level**, a **category**, a **method**, the `check` that implements the method when one exists, a `text` and, where an observed counterfactual exists, a `why`; a rule of the protocol also has an `origin`. A rule of the protocol is a **protocol rule**. The spec's own files are verified by the tests of `check-spec`, which are not rules | "requirement" for a rule of any level, "constraint", "criterion" |
| **level** | how binding a rule is: **requirement**, **recommendation** or **permission** (ISO/IEC Directives Part 2, clause 7); a field of the rule, never a word parsed from its text: the verb of a rule of the spec matches it, and the field is authoritative | "priority", "severity" (a check's, below) |
| **requirement** | a rule of the level requirement: "shall", "shall not" (« doit », « ne doit pas »); in the protocol, the imperative. A product conforms when it holds every requirement of its class; a requirement verified by test has a blocking check | "must" (ISO keeps it for external constraints) |
| **recommendation** | a rule of the level recommendation: "should", "should not" (« il convient de », « il convient de ne pas »); outside conformance; its check reports, whatever its method | "guideline", "soft rule", "best practice" |
| **permission** | a rule of the level permission: "may", never in the negative (« peut »): an element that may be absent, or an act the teacher may do. Possibility and capability ("can", « peut ») are not a level | "can" for a permission |
| **method** | how one knows a rule holds, from the closed list of ISO/IEC/IEEE 29148: **test** (a deterministic run: the scripts of `course/checks/`), **analysis** (reasoning over the whole course: taught-check), **inspection** (a reading by a human or an agent: the review), **demonstration** (the system runs and is observed: the fresh tests). A rule states its method even before its check exists | "taught-check" for a method |
| **category** | what a rule is about, from a closed list, extended when needed: for a course `structure`, `pedagogy`, `writing`, `sources`, `diagrams`; for a protocol rule, its family (the nine families of `course-specs/linear-course/1/teacher/README.md`). A check's category is its rules'; `check-course --category` selects checks by it. The tests of `check-spec` have none | "family" for a category of a course, "kind" |
| **severity** | what a check's failure does, derived from its rules, never declared: a check **blocks** when it verifies a requirement by test (a **blocking check**: a `fail` sets exit code 1 of `course-specs/check-course`), and **reports** in every other case (a **reporting check**: a `fail` is printed, leaves the exit code 0, and its findings are triaged into course issues). The field `severity` of a review finding in the agent workflows (`blocking` or `minor`, `course-batch.js` and `taught-check.js` of `.claude/workflows/`) is a finding's weight, not a check's severity | "warning", "soft check", "hard check" |
| **check** | a verification of a course against its spec, that implements the method of rules of one category and one level: the scripts of a spec MAJOR's `course/checks/` that `check-course` runs (method test) and taught-check (method analysis). Its category and level are its rules', its severity follows from them; `check-course --list` prints each check with its category and severity. The spec's own files are verified by the tests of the spec directives it follows, run by `spec-directives/check-spec` (`spec-directives/1/README.md` section 8), which verify no rule, carry no category and no level, and each failure blocks `check-spec` | "test" (a method, not the check), "lint", "validation" |
| **taught-check** | the check of a `pedagogy` recommendation by analysis, run by agents: the agent workflow that verifies no case asks what the learner has not yet been taught (`taught-check.js` of `.claude/workflows/`, run on demand through `/feyn-taught-check`); it reports | |
| **conformity** | the conformance clause (`spec-directives/1/README.md` section 2): a product, the course (its diagrams included) or the teacher, **conforms** when it holds every requirement of its class, whatever the method that verifies each one. The blocking checks are a necessary condition, not a sufficient one: the review and taught-check do the rest, and a course tag certifies the whole. The lexicons of a spec are not products | "conforming" for a course that only passes the blocking checks, "compliance" |

## How we work

The frame of the work is Kanban, with ADR for the decisions and GitHub flow for the branches
(decision `kanban-frame-of-the-work`): what the frame says is in `docs/kanban.md`, how feyn
applies it in `docs/contributing.md`. Its words below are the frame's; the others name feyn's own
mechanisms, which the frame does not name.

| Term | Means | Not |
|---|---|---|
| **area** | the part of the repo an issue or PR belongs to, derived from the tree: `spec:<name>`, `spec-directives`, `course:<id>`, `teacher`, `site`, `agentic`, `repo` | "domain" (reserved for a course domain in this glossary), "component", "module", "scope" |
| **issue** | the GitHub object; it has no form of its own: it carries a **work item**, of one of two kinds, an **epic** or a **story**, or an **idea**, which has no kind; what it carries gives its body template and its labels (decision `issue-carries-a-work-item-or-an-idea`) | "ticket", "task" |
| **epic** | a work item: an objective delivered in several stories, which closes on a verifiable Done when (common agile and GitHub vocabulary, `docs/kanban.md`): an issue with the label `kind:epic`, titled "Epic: …", in five sections (Objective, Why now, Material, Done when, Out of scope), parent of its stories, split one story at a time when taken; its plan is a **plan comment** on it (decision `themes-and-release-milestones`). No Done when, no epic | "theme", "subject", "initiative", "stream", "phase" |
| **story** | a work item: a unit of work delivered in one PR, with a verifiable Done when (common agile and GitHub vocabulary, `docs/kanban.md`; a story need not be written as a user story): an issue with the label `kind:story`, with or without a parent epic; under an epic, a sub-issue whose PR targets the epic's integration branch; without one, its PR targets `main` and the maintainer merges it (decision `story-with-or-without-an-epic`) | "slice", "task", "sub-task" |
| **idea** | what enters the upstream (`docs/kanban.md`): an issue holding a finding and no solution, in three sections (Where, Why, Observation), with no kind, only its `area:` label, in the Status Idea; it is never converted: the triage creates from it the work items it calls for, then closes it (decisions `issue-carries-a-work-item-or-an-idea`, `idea-is-never-converted`). Its Observation is a section, not a kind | "observation" for the issue, "Backlog" for its Status, "suggestion" |
| **option** | a work item, epic or story, defined but not committed (`docs/kanban.md`): it has the body of its kind, Done when included, in the Status Option, and waits for the maintainer to commit it (set Ready) or close it, one option at a time, at an **option refinement** (`/feyn-refine-option`); until Ready its kind and body may change. A work item a triage creates is born Option unless the maintainer commits it at its creation; one a brainstorm creates is always born Option; a work item the maintainer asks for directly, a story or an epic, is born Option, or Ready on their word (decision `idea-and-option-before-ready`) | "proposal", "candidate" |
| **label** | always qualified: **type** (`type:bug`, `type:course`, `type:improvement`, `type:decision`), set on a work item, never on an idea; **area** (`area:<area>`); **kind** (`kind:epic`, `kind:story`: exactly one on a work item, none on an idea; decision `kind-label-per-work-item`); `blocked:maintainer` (a maintainer decision is awaited; on the issue only); and `stale` (an idea or an option posed before the frame of 2026-11-03, re-read at its triage or option refinement, which removes it). No state label: where an issue stands is its **Status** | |
| **Project** | the GitHub Project "feyn" (number 4) that holds every issue with its Status: what the maintainer looks at in the web interface, through its **views** (read with a query of `.claude/reference/project.md`), and what the agent lists (`gh project item-list`) | "board" for the Project itself, "dashboard" |
| **Status** | the Project's field that says where an issue stands, in this order and nothing else: **Idea** (an idea, to triage), **Option** (a work item defined, not committed), **Ready** (committed, free to take: the **commitment point**), **In progress** (a branch exists), **Ready for review** (the work claims done, the maintainer reviews and concludes: a story without an epic whose PR is open after the fresh-agent review, or with the line `Fresh-agent review: none, direct delivery.`, which the maintainer merges; an epic whose epic PR is handed over, whose Done when the maintainer verifies before merging it; a story of an epic never has it), **Done** (closed; the close reason stays on GitHub). A decision awaited is the label `blocked:maintainer`, on any Status (decision `idea-and-option-before-ready`). It replaces the state labels. Written with a capital when it names the field; the lowercase `status` key of a decision's frontmatter is a different, allowed key | "state" for where the work stands (an issue's `state` is GitHub's open or closed) |
| **commitment point** | where an option is taken and becomes committed work: in feyn, the Status **Ready**, set by the maintainer, or given at creation to a story posed by the orchestrator of a taken epic; from it the work item's form freezes and its Done when becomes the contract (decision `issue-defines-pr-verifies`). What the frame says: `docs/kanban.md`, "The upstream" | |
| **WIP limit** | a limit on the work in progress, the items started and not finished, per Status or for the whole workflow: a new item is pulled only when one leaves. What the frame says: `docs/kanban.md`, "Kanban"; how feyn applies it: `docs/contributing.md` | |
| **triage** | reading the ideas that came in and deciding what each one calls for: the work items it calls for, each citing it, the idea then closed as completed; or nothing, the idea closed as not planned, with the reason. In feyn, run with the maintainer on the ideas they name, one at a time (`/feyn-triage`); an option is not triaged, it goes to an **option refinement**. What the frame says: `docs/kanban.md`, "The upstream" | "Backlog pass", "grooming" |
| **option refinement** | the analysis of one named option against the purpose of feyn (which product consumes it, `docs/vision.md`) and against the repository (what changed in the files it names since it was last updated, the work items and ideas that cover or overlap it), up to a decision on it alone: commit it (set Ready), rework it, open a brainstorm from it (what it builds on has changed), merge it, split it, fold it into an epic or close it; run with the maintainer, one option at a time (`/feyn-refine-option`). It is not a **replenishment**: it never reviews all the options nor chooses among them. What the frame says: `docs/kanban.md`, "The upstream" | "replenishment", "grooming" |
| **replenishment** | the Kanban review of all the options against the capacity of the downstream, choosing which enter Ready. Not practised in feyn, where a commitment is decided option by option, at an **option refinement**. What the frame says: `docs/kanban.md`, "The upstream" | "option refinement" |
| **policy** | what the workflow asks, written down where everyone reads it: what an item must hold to enter or leave a Status, the WIP limits, what is done first, who decides what; feyn's are in `docs/contributing.md`, the decisions and the skills. What the frame says: `docs/kanban.md`, "Kanban" | "rule" (a spec's), "convention" |
| **draft** | a PR that cannot be merged until it is marked ready (`gh pr ready`); `/feyn-pull-request` opens one when a maintainer decision is awaited (the issue, not the PR, carries `blocked:maintainer`), and under `/feyn-deliver-story-alone` and `/feyn-deliver-epic` every PR is one until its review and corrections are done (marked ready at the hand-over of a story without an epic, `/feyn-deliver-story-alone` step 5, or at the merge of a story of an epic into its integration branch, `/feyn-deliver-epic` step 2) | "WIP" for a draft PR |
| **blocked** | two senses, never mixed. "Blocked by #n": a blocked-by link between issues (decision `blocked-by-links-for-dependencies`), lifted when the blocking issue closes. `blocked:maintainer`: a maintainer decision is awaited, on the issue only, lifted when the maintainer removes the label | "on hold", "Needs Decision" (a Status removed) |
| **work session** | always qualified (the other sense is a **teaching session**): one Claude Code conversation on the feyn repository: a **brainstorm** (with the maintainer, subject by subject, ending in a plan of work items, `/feyn-brainstorm`), the delivery of a story without an epic (`/feyn-deliver-story-alone`) or of an epic (`/feyn-deliver-epic`), a triage (`/feyn-triage`), an option refinement (`/feyn-refine-option`), a construction task (historical). A construction task left a **session note** in `construction/notes/`, removed on 2026-10-31 and read at `2c16adf3e66a` (decision `construction-in-history`) | "session" alone |
| **integration branch** | the branch an epic is delivered on: cut from `main` by the epic's orchestrator when the epic is taken, named like an issue branch after the epic (`<type>/<epic>-<slug>`); each story of the epic is a PR to it, reviewed by a fresh agent and merged by the orchestrator; `main` is merged into it, never rebased; it reaches `main` only by its **epic PR**. Not a channel (decision `epic-on-integration-branch`) | "epic branch", "feature branch", "develop", "staging branch" |
| **epic PR** | the PR from an epic's integration branch to `main`, its body starting with `Closes #<epic>`: handed over to the maintainer once the last story is merged, the whole branch reviewed by a fresh agent and no open question left; the maintainer validates the whole epic by merging it (squash), which closes the epic | "integration PR", "final PR", "release PR" |
| **open question** | a choice of a story of an epic that departs from the epic's Done when or adds structure (a new file, a category, a marker, an exception to a principle), put to the maintainer at once as a line of the plan comment and a comment on the epic; the work goes on, and the epic PR is handed over only when none remains | "pending decision", "escalation", "blocker" |
| **direct delivery** | a story, alone or under an epic, of one edit with no behaviour, named `direct` by the maintainer at its creation (`/feyn-issue`), its To do opening with the line "Direct delivery": the maintainer's work session delivers it with `/feyn-issue-branch` and `/feyn-pull-request`, without a contributor or a fresh-agent review; its PR's Checks say `Fresh-agent review: none, direct delivery.` (`docs/contributing.md`, moment 2). A delivery policy, not a form | "direct path" (that is `/feyn-pull-request` run without `/feyn-deliver-story-alone`, its fresh-agent review included) |
| **milestone** | a release target: named after the tag that closes it (`linear-course/v1.0.0`, `po-essai/v0.2.0`), holding the stories that must close before the tag, created when a release is in sight; an epic may target one; tooling has none | "sprint", "phase", "version" for the milestone itself |
| **stage** | historical: one of the five milestones of the construction plan of 2026-10-27 (stage 0 to 4), abandoned on 2026-10-29 for epics; the word stays only in `construction/` (read at `2c16adf3e66a`, decision `construction-in-history`) and in old issues | "lot", "phase", "sprint", "iteration" |
| **batch** | a set of concepts written in one run of the agent workflow `course-batch.js` of `.claude/workflows/` (ex `course-lot`), through `/feyn-course-batch` | "lot", "chunk" |
| **decision** | a recorded decision: one file by slug in a `decisions/` folder, with its counterfactual. "ADR" is never the name of one decision, nor in a path: it names the frame's complement, the practice of recording decisions (`docs/kanban.md`, "ADR"; decision `kanban-frame-of-the-work`) | "ADR" for one decision or in file names, "RFC", "design doc" |
| **counterfactual** | the first line of a decision, `Without this, <who acts> would…`: the wrong act that whoever it binds (an agent, the common case, a contributor, the teacher, a workflow, the maintainer) would commit without it, and what that breaks | "rationale", "motivation" |
| **fresh test** | a run of the teacher in a disposable classroom, following a **test scenario**, judged slug by slug: `classroom-builder/fresh-test` builds the classroom, runs the teacher with `claude -p` turn by turn (Sonnet), and judges the transcript by a script (the form rules) and a fresh agent (`claude -p` on Sonnet, no tool: the others); the implementation of the method demonstration | "e2e", "smoke test", "simulation" |
| **test scenario** | one YAML file of a spec MAJOR's `teacher/tests/`: the learner memory a fresh test starts from, the learner's messages in order, the acts expected of the teacher and the slugs of the rules they exercise (`teacher/tests/README.md`) | "test case", "script", "fixture" |
| **review** | a reading of a change against the spec by an agent or a human | "audit", "QA" |
| **skill** | a Claude Code skill of `.claude/skills/`, folder and name prefixed `feyn-`, invoked as `/feyn-<name>` or loaded from its description; a **job skill** does the job of one moment of the work and is named by a verb (`feyn-deliver-story-alone`, `feyn-brainstorm`); the **work-cycle tooling** is the other skills, called by the job skills or directly for a one-off act, each named by what it produces or handles (`feyn-issue-branch`, `feyn-pull-request`); "tooling" alone is the build, site and teacher code; a **teacher skill** is a skill of a classroom's `.claude/skills/`, built by `classroom-builder/` from the moments of the **composition** as the spec MAJOR's `teacher/build/` renders them, one per moment that has rules, named `feyn-teacher-<moment>` (`feyn-teacher-onboarding`, `feyn-teacher-stop`), apart from Claude Code's own (`/resume`) | "command", "prompt", "recipe" |
| **agent workflow** | a Claude Code multi-agent script in `.claude/workflows/`; its name (`meta.name`) is `feyn-<script>-workflow`, so that the skill listing tells it from a skill | |
| **project subagent** | a Claude Code custom subagent of `.claude/agents/`, named `feyn-<role>` (`feyn-pr-reviewer`): a reused brief as its system prompt, its tools limited by its frontmatter, spawned by name (`subagent_type` of `Agent`, `agentType` of an agent workflow's `agent()`) | "persona", "bot" |
| **CI workflow** | a GitHub Actions file in `.github/workflows/` | "pipeline", "action" |
| **Project workflow** | a built-in automation of the Project ("Auto-add to project", "Auto-add sub-issues to project", "Item added to project", "Item closed"), turned on in the web interface; `.claude/reference/project.md` lists which are on | "automation", "workflow" alone |
| **template** | always qualified: **course templates** (`course-specs/<name>/<MAJOR>/course/templates/`, model files of a course), **learner templates** (`course-specs/<name>/<MAJOR>/teacher/templates/learner/`, model files of learner memory, in French for now), **teacher template** (`classroom-builder/CLAUDE.template.md`, part of the Claude Code realisation of the **composition**, filled from the parts the spec MAJOR's `teacher/build/` renders), **issue template**, **body template** (`.claude/reference/*-body.md`: the body of an epic, a story, an idea or a decision, one per form, and the **PR body template**, `.claude/reference/pr-body.md`) | "template" alone, "boilerplate", "scaffold" |
| **channel** | where a build is served from: **prod** (a course tag), **next** (`main`), **preview** (a PR) | "environment", "stage", "env" |
| **release** | tagging a course version (`<id>/vX.Y.Z`) and deploying prod; "publish" means a release, never a build | "deploy" alone, "ship" |
| **course version** / **spec version** | two of the three versioned objects, the third being the **spec directives** (decision `versioned-objects-and-spec-layout`); tooling has a **commit sha**, no version | "site version", "teacher version" |
