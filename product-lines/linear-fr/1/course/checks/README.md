# Checks of `linear-fr`

Scripts that verify a course against the rules of `course/rules.yaml` (described by `course/README.md`; listed in the MAJOR's `README.md` section 5), run by `check-course`, beside the agent workflow `taught-check.js`, which it does not run (below); the tests of the spec's own files (those `spec.yaml` declares, the teacher's `README.md` and `rules.yaml` among them, with `README.md`, `CHANGELOG.md` and `decisions/`), run by `spec-directives/check-spec`, belong to the spec directives this MAJOR follows (`spec-directives/1/tests/`) and are described in `spec-directives/1/README.md` section 4. Node 20.19 or later (the floor of the package of the directives), CommonJS, run under `mise exec` like every tool here, with the `lib/` and the dependencies of the directives MAJOR that the MAJOR's `spec.yaml` declares (`directives: 1`, so `spec-directives/1/package.json`; decision `checks-use-ajv-and-yaml`): `directives.js` reads that line and loads them through a `createRequire` on that `package.json`; the course is read by the parser of this MAJOR, `course/parser.js`, which `check-course` gives that `lib/` (`directives.lib`), its concept references, its claim marks and its glossary by the readers beside it, `course/refs.js`, `course/claims.js` and `course/glossary.js`, which the checks that read them give that `lib/` too. The course's YAML is read by the package `yaml` in YAML 1.2 mode, through `lib/yaml-lines.js`, which keeps the line of each key and item so a failure points at `file:line`; ajv compiles the schemas of `course/schemas/` through its class `Ajv2020` (JSON Schema 2020-12); Markdown is read by `lib/md.js`, line by line, for its blocks (the frontmatter, the headings, the sections, the tables), and by `lib/mdast.js`, the CommonMark reader on `mdast-util-from-markdown` that the site's parser shares, for inline Markdown, the claim marks first (`course/claims.js`; decision `claim-marks-read-by-one-reader`); SVG by `lib/xml.js`, which covers the subset the spec uses. Each rule of `course/rules.yaml` names in `check` the script that verifies it, and `check-course` takes its checks from there (`rules.js`, beside it). The form of the concept file is read from `course/form.yaml` (`check-course` passes it to the parser of this MAJOR, `course/parser.js`, which finds the parts of each `concept.md`, its units and their fields, for every check that reads them): `concept-file`, `unit-contract`, `case-coverage` and `teacher-message-length` hold a course to it, and `conventions`, `glossary-order` and `unit-additions` take from its `readers` the parts the learner reads; the form of the course files is read there too, by `course-yaml` (`course_map`, `logo`) and `course-files` (`plan`, `domain_file`, `storyline`). `course-yaml` validates `course.yaml` through `Ajv2020` and `course/schemas/course.schema.yaml`, `concept-file` the frontmatter of `concept.md` through `course/schemas/concept-frontmatter.schema.yaml`, and `sources` the course's `sources.yaml` through `course/schemas/sources.schema.yaml`, a failure mapped from ajv's instance path to its `file:line` (`lineOfError` of `lib/yaml-lines.js`); neither re-checks in its own code what a schema says.

## Install

```
mise exec -- npm ci --prefix spec-directives/1
```

From the repository root, once per clone or worktree, and again when `package-lock.json` changes: `npm ci` installs the locked versions in `spec-directives/1/node_modules/`, which git ignores. The command has no `cd`, so an agent in a worktree can run it. Without it, `check-course`, `test-fixtures`, `product-lines/check-course` and `spec-directives/check-spec` stop with one line giving that command (exit code 2); a missing `spec.yaml`, or a `directives` MAJOR with no folder, stops them the same way.

## Run

```
mise exec -- product-lines/check-course courses/<id>
mise exec -- product-lines/check-course courses/<id> --category pedagogy
mise exec -- product-lines/check-course courses/<id> --only drawing-contract
mise exec -- product-lines/check-course courses/<id> --only concept-file,unit-contract --concept 9
mise exec -- product-lines/linear-fr/1/course/checks/check-course --list
```

The checks come from the rule file of a course (the MAJOR's `README.md` section 3; decision `severity-from-level-and-method`), read by `rules.js`: `check-course` runs, in one run, every check named by the `check` of a rule of `course/rules.yaml` whose method is test. A check's category and level come from its rules, which `rule-files` (`check-spec`) holds to one value of each classification per check, one category and one level, and its severity follows: it **blocks** when its rules are requirements verified by test, otherwise it **reports**. A failure of a blocking check sets exit code 1; a failure of a reporting check is printed the same way, its findings triaged into course issues, and leaves exit code 0. The blocking checks run first, then the reporting ones, each in the order of `course/rules.yaml`; no list of checks is written in `check-course`.

A check runs on a course when its method is test and its script is in this folder. The tests of `check-spec` (`spec-directives/1/README.md` section 4) verify no rule: `check-course` neither runs nor lists them. A check of another method is not run here: `taught-check` (analysis) is an agent workflow kept in this folder, `taught-check.js`, which `check-course` does not run, run as `product-lines/linear-fr/1/README.md` section 5 says; and a rule verified by inspection has no check, the review reads it. `--list` names every check, the ones not run here with how they run.

`product-lines/check-course` reads `spec: linear-fr@<MAJOR>` in the course's `course.yaml` and runs `product-lines/linear-fr/<MAJOR>/course/checks/check-course` with the same arguments; it refuses an unknown spec or MAJOR, naming it, with exit code 2. The `spec:` line names the MAJOR, whose `spec.yaml` names, by its `directives:` line, the directives MAJOR whose `yaml` package (in `spec-directives/<MAJOR>/node_modules/`) then reads `course.yaml`: the dispatcher needs that `npm ci` too. This folder's `check-course` runs this MAJOR's checks directly, `--list` with no course included.

One line per passing check (`<id>: ok`), one line per failure (`<id>: fail: <file>:<line> <message>`, the file relative to the course folder), whatever the severity; then one summary line, `summary: <n> blocking checks, <n> failed (<ids>); <n> reporting checks, <n> failed (<ids>); exit <code>`. The exit code is 0 when no blocking check fails, 1 when one fails or a check crashes, 2 on a usage error, when the rule files cannot be read or when the dependencies are not installed.

| Option | Does |
|---|---|
| `--category <c>[,<c>]` | runs the checks of those categories only (repeatable): a closed list, the categories of a course in `course/rules.yaml` (`structure`, `pedagogy`, `writing`, `diagrams`, `sources`); an unknown one is a usage error |
| `--only <id>[,<id>]` | runs those checks only (repeatable); an unknown id (a test of `check-spec` among them), the id of a check not run here, or an id outside `--category` is a usage error |
| `--concept <number>` | the per-concept checks (`concept-file`, `unit-contract`, `unit-additions`, `case-coverage`, `teacher-message-length`, `conventions`, `drawing-contract`, `sources`, `sources-coverage`, `glossary-order`) look at that concept only (`sources` and `sources-coverage` read the claim marks of every concept, to join `sources.yaml` to them, and report on that concept's claim marks and quotes, and on `sources.yaml` itself), and `course-yaml` demands only that concept's folder and does not look for unlisted folders in `concepts/`: for a migration in progress, or a creation concept by concept, when the other concept folders do not exist yet ("The checks of each step of the creation", below) |
| `--lexicon <file>` | reads the lexicon of the course files from `<file>` instead of this MAJOR's `course/lexicon.yaml` (the fixtures' lexicons, `test-fixtures`) |
| `--list` | prints every check of `course/rules.yaml`, `--category` applied, in the order of the run: its id, its category, its severity (`blocks` or `reports`), and for a check not run here, how it runs; no course needed |

The flag `--quality`, removed, is a usage error whose one line names its replacement: the default run, which holds the reporting checks, or `--category`.

That a sentence which states a claim is marked, that a nature fits what it claims, and that a quote is the shortest phrase that proves its claim are reviewed; that a `checked` was written by the human who verified is reviewed too.

## The checks of each step of the creation

Until `products/creator/` holds the creation path (epic #522), this section names the steps of the creation of a course and the checks each runs. Foundations, once: F1 to F4; then concept by concept, C1 to C5 (C6, teaching the concept, once the teacher is brought up to date with the course: epic #757), a concept finished before the next starts; D1 for a domain, once its concepts are written. A step runs its command at once, on what it has just written; `<course>` is `courses/<id>`, `<n>` the number of the concept being written.

The checks stay strict: there is no draft state, and a check reads a whole file or the whole course. A failure that names what a later step writes is that step's work, not a defect: the last column says which ones to expect. A step is done when its command prints no other failure, a bold that `unit-additions` reports and the creator keeps for emphasis excepted. The course is done when `product-lines/check-course <course>`, with no option, exits 0.

| F2 the course plan | the domains of `course.yaml`, `plan.md` « Progression » | `product-lines/check-course <course> --only course-files` | `storyline.md`, `glossary.md` (F4) |

| F4 the world | `storyline.md`, its world without « Faits fixés »; `glossary.md`, its table without rows | `product-lines/check-course <course> --only course-files` | nothing: it passes |
| C1 the skeleton | `concept.md`: its title, `# Concept <n> : <title>` (an annex `# Annexe <id> : <title>`), the title of `course.yaml`; the sections, `## Section <id> : <title>`, and their units, `### Unité <id> : <title>`, one at least per section, each with its first block, `#### Leçon`, and one line of matter | `product-lines/check-course <course> --concept <n> --only concept-file,unit-contract` | the other blocks of each unit (C2); the head, « L'essentiel » (C3) |
| C2 each unit and its additions | a unit's blocks, in the order of writing: teach, `#### Leçon` (« Matière », then « Idées fausses », each misconception named, with its « Racine » and its « Correction »); ask, `#### Cas du fil rouge` (its case, under its heading `##### Cas : <title>`, « Ancrage », « Question », « Réponse attendue », « Idées fausses en jeu », the misconceptions of the unit it makes tempting, then its supplementary cases in the same form, each misconception of the unit named by a case at least); instruct, `#### Consigne au professeur` when the unit has one, the boundary of its matter, only what a competent teacher would otherwise do differently in this unit (rule `teacher-note-beyond-competent-teacher`), where a move of the course goes (rule `course-question-in-teacher-note`); « Leçon » and « Cas du fil rouge » are published, « Consigne au professeur » never; its additions: a fact an anchor uses, in « Faits fixés » of `storyline.md` naming the unit; a term it puts in bold, in `glossary.md` (`unit-additions` reports a bold that is no term); a claim of a published field marked where it is written, `[the text claimed](cours)` until its sources are written (C4) | `product-lines/check-course <course> --concept <n> --only unit-contract,unit-additions,conventions,course-files,case-coverage,teacher-message-length,glossary-order,typography` | a concept reference to a concept not yet written, and a glossary term of that concept in its sentence (`glossary-order`, which reports) (that concept's C1) |
| C3 the head and foot | the head, `## L'essentiel`, then its text; the foot, `## Clôture`, then its blocks, `### Se vérifier`, `### Approfondissement`, `### Consigne au professeur` (the boundary of the concept's matter, only what a competent teacher would otherwise do differently in the whole concept, rule `teacher-note-beyond-competent-teacher`; a move of the course that holds for the whole concept, rule `course-question-in-teacher-note`), those it has (no « Clôture » without one); its claims marked, as at C2 | `product-lines/check-course <course> --concept <n> --only concept-file,conventions,glossary-order,typography` | a concept reference to a concept not yet written, as at C2 |
| C4 the sources | each marked claim its nature and its sources, `[the text claimed](consensus:S1 "name")`, its name for a sourced claim; `sources.yaml` at the root of the course: each source once (a source another concept already cites keeps its id), its CSL fields, its `kind`, `control` and `independence`, the quotes that prove each claim citing it, the `holder` of an `école` claim; no `checked`, which only a human who verified writes (the third addition of a unit) | `product-lines/check-course <course> --concept <n> --only concept-file,sources,sources-coverage` | `sources-coverage`, which reports each claim no human has checked yet |
| C5 the diagrams | each diagram, its SVG and its declaration in the frontmatter at its unit | `product-lines/check-course <course> --concept <n> --only drawing-contract,concept-file` | nothing: it passes |
| D1 the domain file | `domains/<number>-<slug>.md`, « Le problème » and « Un cas qui traverse le domaine » | `product-lines/check-course <course> --only course-files,course-yaml` | the folders of the concepts not yet written (their C1), the files of the other domains (their D1) |

`course-yaml` asks for every concept folder and every domain file `course.yaml` names, so it passes only once each exists; under `--concept <n>` it asks for that concept's folder only, but still for every domain file. The rules by inspection of a step (the content of a field, the restatement between a unit's matter and its cases, the facts an anchor uses, the claims to source) are the review's: `course/rules.yaml` lists them in the group of each section of `course/README.md`.

## Tests of the spec itself

The tests of the spec's own files, run by `spec-directives/check-spec <spec-dir>`, belong to the spec directives this MAJOR follows: their list, what each verifies, their fixtures and how to run them are in `spec-directives/1/README.md` section 4.

## Tests

```
mise exec -- product-lines/linear-fr/1/course/checks/test-fixtures
```

It tests the course fixtures and the dispatcher; the spec fixtures, under `spec-directives/1/tests/fixtures/`, are tested by `spec-directives/1/tests/test-fixtures` (`spec-directives/1/README.md` section 4).
